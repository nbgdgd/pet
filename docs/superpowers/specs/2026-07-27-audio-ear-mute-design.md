# AudioEarMute — глушение одного наушника

Дата: 2026-07-27

## Задача

Полноразмерные Bluetooth-наушники надеты на обе уши. Нужно программно заглушить одну
чашку, чтобы ухо отдыхало, продолжая слушать другим. Переключение — левый / правый /
стерео — на лету, без перезапуска приложений и без перезагрузки системы.

## Почему прошлая попытка не сработала

`AudioChannelRouter` (существующий проект в репозитории) крутил
`IAudioEndpointVolume::SetChannelVolumeLevelScalar` — поканальную громкость **эндпоинта**.
На Bluetooth это не работает: A2DP Absolute Volume передаёт громкость на сами наушники
одним общим значением, поканальное разделение теряется. Программа также требовала правки
реестра и перезагрузки.

## Решение

Использовать `IChannelAudioVolume` — поканальную громкость **аудиосессии** (отдельного
приложения). Она применяется программным микшером Windows до отправки потока на
устройство, поэтому свойства Bluetooth-эндпоинта на неё не влияют.

Ноль сторонних драйверов, ноль перезагрузок, ноль дополнительной задержки.

### Отвергнутые альтернативы

| Вариант | Почему нет |
|---|---|
| VB-Cable + свой WASAPI-микшер | Гарантированно работает, но требует стороннего драйвера и добавляет 20-30 мс. Держим как фолбэк. |
| Equalizer APO | Нулевая задержка, но на Bluetooth-эндпоинтах цепляется нестабильно — риск повторить прошлый провал. |
| `IAudioEndpointVolume` по каналам | Уже провалился (см. выше). |

## Архитектура

```
Program.cs             точка входа, STA, запуск TrayApp
TrayApp.cs             NotifyIcon, меню, глобальные горячие клавиши, иконка режима
AudioEngine.cs         выделенный MTA-поток: вся работа с Core Audio
CoreAudioInterop.cs    COM-интерфейсы WASAPI (объявления, без логики)
MuteLogic.cs           чистая логика: режим -> (L,R), фильтр сессий. Без COM.
Config.cs              %APPDATA%\AudioEarMute\config.json
DiagnosticsForm.cs     отчёт по сессиям с обратным чтением громкости
```

### Разделение потоков

Core Audio требует MTA для того, чтобы `IAudioSessionManager2::RegisterSessionNotification`
доставлял уведомления. WinForms требует STA. Поэтому:

- STA-поток — только UI (трей, меню, горячие клавиши, диалоги).
- MTA-поток — весь Core Audio. Владеет `IMMDeviceEnumerator`, менеджером сессий,
  подписками. Принимает команды через очередь.

UI никогда не трогает COM-объекты напрямую. Команда `SetMode` кладётся в очередь,
результат возвращается через callback в UI-поток.

### Режимы

| Режим | Левый канал | Правый канал | Смысл |
|---|---|---|---|
| `Stereo` | 1.0 | 1.0 | Обычный звук |
| `LeftOnly` | 1.0 | 0.0 | Правое ухо отдыхает |
| `RightOnly` | 0.0 | 1.0 | Левое ухо отдыхает |

## Поток данных

1. Старт: читаем конфиг, получаем режим.
2. MTA-поток создаёт `IMMDeviceEnumerator`, берёт дефолтный Render-эндпоинт
   (`eRender` / `eMultimedia`).
3. Активирует `IAudioSessionManager2`.
4. **Сначала** вызывает `GetSessionEnumerator`, **затем** `RegisterSessionNotification`.
   Порядок обязателен: без предварительного перечисления Windows не доставляет
   уведомления о новых сессиях.
5. Регистрирует `IMMNotificationClient` на смену устройства по умолчанию.
6. Применяет режим ко всем сессиям.
7. Далее режим переприменяется по трём триггерам:
   - `OnSessionCreated` — запустилось новое приложение;
   - `OnDefaultDeviceChanged` — наушники переподключились;
   - таймер 2 с — страховка от реактивации истёкших сессий, о которых
     `OnSessionCreated` не сообщает.

Режим живёт в программе, а не в системе. Любое событие означает «применить заново».

## Применение к сессии

Для каждой сессии из перечисления:

1. `GetState` — пропустить `AudioSessionStateExpired`.
2. QI на `IChannelAudioVolume`, `GetChannelCount`.
3. Если каналов != 2 — пропустить, увеличить счётчик неподдержанных.
4. `SetChannelVolume(0, L, ctx)`, `SetChannelVolume(1, R, ctx)`.

## Обработка ошибок

- **Моно-сессия** (`ChannelCount == 1`). Разделить нечего. Глушить целиком нельзя — потеряется
  звук. Не трогать — попадёт в отдыхающее ухо. Решение: пропускаем, счётчик выводим
  в тултип трея (`2 моно-сессии не поддержаны`). Явно, а не молча.
- **Сессия умерла между перечислением и записью.** COM бросает исключение.
  `try/catch` вокруг каждой сессии отдельно: одна мёртвая не срывает обработку остальных.
- **Аварийное завершение оставляет ухо глухим.** Windows хранит громкость сессий в реестре,
  само не восстановится. Защита с двух сторон:
  - `try/finally` + обработчик `ProcessExit` возвращают `(1.0, 1.0)` на всех сессиях;
  - на старте, если сохранённый режим `Stereo`, принудительно раскатываем `(1.0, 1.0)`
    по всем сессиям — подчищаем за прошлым падением.
- **Эксклюзивный режим WASAPI** (ASIO, некоторые плееры) идёт мимо микшера, воздействовать
  нельзя. Редкий случай, выявляется диагностикой.
- **Нет устройства вывода.** Трей показывает `Нет устройства`, движок ждёт
  `OnDefaultDeviceChanged`.

## Диагностика

Пункт меню трея открывает окно с отчётом: по каждой сессии — имя процесса, состояние,
число каналов, результат `SetChannelVolume` и **обратное чтение** `GetChannelVolume`.

Критерий провала подхода: записали `0.0`, прочиталось не `0.0`. Это объективный признак,
что микшер игнорирует поканальную громкость на этом железе и нужен фолбэк на VB-Cable.
Оценка «на слух вроде тише» критерием не является.

## Горячие клавиши

| Сочетание | Действие |
|---|---|
| `Ctrl+Alt+Left` | Только левый (правое ухо отдыхает) |
| `Ctrl+Alt+Right` | Только правый (левое ухо отдыхает) |
| `Ctrl+Alt+Up` | Стерео |

Регистрируются через `RegisterHotKey` на скрытом окне UI-потока. Если сочетание занято
другой программой, регистрация тихо не удаётся — трей показывает это в тултипе, меню
продолжает работать.

## Конфигурация

`%APPDATA%\AudioEarMute\config.json`:

```json
{
  "mode": "Stereo",
  "hotkeys": { "leftOnly": "Ctrl+Alt+Left", "rightOnly": "Ctrl+Alt+Right", "stereo": "Ctrl+Alt+Up" }
}
```

Битый или отсутствующий файл — берутся значения по умолчанию, файл перезаписывается.

## Тестирование

**Юнит-тесты** (`AudioEarMute.Tests`, xUnit) на чистую логику из `MuteLogic.cs`:
маппинг режима в пару громкостей, решение о пропуске сессии по состоянию и числу каналов,
разбор горячих клавиш. COM не участвует, железо не нужно.

**Ручная проверка:** пункт меню генерирует WAV — 440 Гц только в левом канале, 880 Гц
только в правом, 5 с — и проигрывает его через `System.Media.SoundPlayer`. Плеер создаёт
собственную сессию, поэтому проверяет и применение режима к новой сессии тоже.
Прогон трёх режимов на слух + отчёт диагностики с обратным чтением.

## Результат проверки на целевой машине

Прогон `AudioEarMute.exe --diagnose` 2026-07-27: 7 из 7 стереосессий приняли поканальную
громкость, обратное чтение совпало с записанным (`L=1.00 R=0.00`). Подход подтверждён,
фолбэк на VB-Cable не требуется.

Попутно выяснилось: устройством вывода по умолчанию на машине выступает виртуальное
`FxSound Speakers (FxSound Audio Enhancer)`, а не сами наушники. Наше вмешательство
происходит до обработки FxSound. Если у FxSound включён эффект, смешивающий каналы,
заглушенный канал может наполниться обратно — это ограничение вынесено в README.

## Автозапуск

Добавлен после первой итерации по запросу пользователя.

Первая реализация писала в `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`.
Она работала, но выглядела как поломка — см. разбор ниже. Итоговая реализация —
задача планировщика.

После перезагрузки значок в трее не появился. Журнал
`Microsoft-Windows-Shell-Core/Operational` показал обратное:

16:22:27  9707  Начато выполнение "ProtonDrive.exe" -quiet

Автозапуск сработал. Корневая причина в другом: explorer выполняет записи `Run`

Задержку создаёт не наш код, и ускорить свою запись внутри очереди нельзя.

### Итоговая реализация

Задача планировщика `AudioEarMute`: триггер `LogonTrigger`, `LogonType=InteractiveToken`,
`RunLevel=LeastPrivilege` — прав администратора не требует (проверено на непривилегированном
процессе). Задачи по входу запускаются параллельно, вне очереди explorer.

Существенные настройки задачи:

- `ExecutionTimeLimit=PT0S` — значение по умолчанию (3 дня) убило бы приложение в трее;
- `MultipleInstancesPolicy=IgnoreNew` — повторный вход не плодит копии;
- `DisallowStartIfOnBatteries=false`, `StopIfGoingOnBatteries=false` — на ноутбуке
  автозапуск нужен не меньше.

Запись в `Run` удаляется при включении автозапуска, а оставшаяся от прежней версии
переводится на задачу при первом запуске: иначе программа поднималась бы дважды.

Галочка в меню читает фактическое состояние, а не хранит собственный флаг: иначе после
чистки автозагрузки сторонней утилитой интерфейс показывал бы неправду.

Автозапуск указывает на `dist\AudioEarMute.exe` — самодостаточную однофайловую сборку.
Путь в `bin\Release\` не подходит: его сносит любая пересборка, и автозапуск сломался бы
молча. Самодостаточность также снимает зависимость от установленного .NET.

При старте вызывается `RepairPathIfMoved`: если запись есть, но указывает на
несуществующий файл, путь переписывается на текущий. Условие «файла больше нет»
обязательно — без него вторая копия программы перехватывала бы автозапуск у первой.

### Чтение зарегистрированного пути

Путь читается из файла `%WINDIR%\System32\Tasks\AudioEarMute`, а не из вывода
`schtasks /Query /XML`. При перенаправлении schtasks печатает в консольной кодовой
странице (на целевой машине CP866), хотя внутри XML объявляет UTF-16; однобайтовых
кодовых страниц в .NET нет без пакета `System.Text.Encoding.CodePages`, и путь
с кириллицей превращался бы в мусор. У файла задачи есть BOM, поэтому
`File.ReadAllText` определяет кодировку сам. Файл читается владельцем задачи
без прав администратора.

`schtasks` используется только для создания и удаления — разбирается лишь код возврата.

## Границы

Не входит в объём: фолбэк на VB-Cable (пишется только если диагностика покажет провал),
регулировка баланса плавным ползунком, обработка сессий записи.
